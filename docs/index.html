The core never names a tool, an identifier, or a language. Everything specific to a repository enters from below; everything specific to an agent enters from above. Swap either side without touching the middle — that is the whole design, and everything else on this page is a consequence of it.

01 — Why a seam

Most agent setups rot because the playbook and the project are the same file

The instinct when an agent misbehaves is to add another paragraph of instruction. Do that for a few months and the instructions have absorbed the tracker's identifiers, the compiler's invocation, and one codebase's private exceptions. The result works beautifully in exactly one repository.

The fix isn't more instruction. It's a boundary. A playbook that says run the project's declared compile check and require zero errors is portable. One that names a specific compiler command is a document about that toolchain wearing a general-purpose costume. Same for the tracker: move the ticket to the project's in-progress state travels; a hardcoded database identifier does not.

So the harness is one middle layer with sockets on both faces. What's universal is the method: how work gets captured, how it is decided that a task is genuinely finished, and what happens when it isn't. What's local is every noun.

02 — The five playbooks

Capture is cheap and constant. Execution is expensive and deliberate.

The central split: writing work down happens whenever a thought arrives, in any session, and starts nothing. Doing the work happens when the operator decides, and drains a queue.

PlaybookWhat it doesWhat it must never do
create-task Reconnaissance in the code, then a short interview, then a ticket carrying a reproduction, a verified root cause where one is findable, and an acceptance criterion. Enqueues it. Write feature code. Commit. Start the work.
start-task Spec-driven planning for the rare ticket that earns it: explore, propose, specify, design, break into tasks. Stops at the planning boundary. Implement. A three-line fix never sees a spec.
pipeline Status, and the engine: take the top ticket, dispatch it to a fresh sub-agent, gate it, commit it, update the tracker, continue. Pause, resume, skip, resync. Deploy. Push. Change branch. Revert on failure.
review-and-fix Independent blind review, triage, fix, run the project's real checks, then a fresh blind re-review against the final diff. Caps its own loop. Trust its own opinion when an executable check exists.
ship Push the working branch and open the run's pull request as a draft, body assembled from the tickets it contains; update it on each later commit; mark it ready when the run ends. Moves each included ticket to the in-review state. Merge. Force-push. Push to the default branch. Request reviewers.

One pull request per run, not per ticket

A run works every ticket on one branch, so a PR per ticket is not available — they would all be the same branch. The playbook is therefore idempotent: the first commit creates the PR, later commits update it, and the end of the run marks it ready. A project that wants a PR per ticket needs a branch per ticket, which is a different branch policy and a config decision, not a different playbook.

It opens as a draft from the first commit on purpose — continuous integration starts early and work is never stranded if a run dies, without waking reviewers on a branch that is still growing.

The PR is always publishable, and that falls out of the failure doctrine rather than being enforced: work from a blocked task goes to a stash and is never committed, so the branch only ever contains verified work.

Pushing is an authorised action, not an assumed one

Everything before this point is local and reversible. Pushing is outward-facing: it reaches teammates, triggers pipelines, and cannot be quietly undone. So the harness treats it as requiring explicit standing authorisation recorded in config, and refuses to start a run on the default branch — because auto-push plus a default branch means pushing straight to it.

Agents straddle the seam on purpose

The review-and-fix playbook launches three: a standard reviewer, a critical reviewer for high-risk diffs, and a fixer. Their behaviour is core — identical in every project. Their tool list and model are generated from the project config, because what an agent may touch depends on the repository it is standing in.

The reviewers are given read-only tool lists, so they are read-only by construction rather than by instruction — an agent that physically cannot write cannot be talked into writing. The fixer gets whatever this project's verification actually needs. When the gate runs through an editor or tool integration and the fixer lacks its tools, it edits blind and reports fixes it never validated, so the installer refuses to leave that silent.

Why execution delegates to a sub-agent

The orchestrator stays thin on purpose: read the queue, pick a ticket, hand it off, commit, move on. Implementation happens in a fresh context that dies with the task. The eighth ticket of a run therefore begins with the orchestrator as clear-headed as the first — which is the difference between a queue that drains and one that degrades into confident nonsense around item four.

Serial, one ticket at a time, one branch, no worktrees. Parallelism across a single branch buys merge conflicts and diffs nobody can attribute.

An agent without a sub-agent primitive still runs every playbook; it just runs execution in the main thread and loses that context hygiene. The adapter declares the limitation so the playbook can shorten its runs instead of pretending.

03 — Four layers

Who you are, where you are, how the work is done, what's wired

Four orthogonal axes. Change one without touching the others, or the seam has failed.

L0

Operator profile — the who

Sits under everything and travels with the person rather than the repository. One document describing how the operator works, what they refuse, and which context they are in. Loaded by every agent in every project so behaviour is identical across a work repo on Tuesday and a personal one on Sunday.

One per human · global

L1

Core playbooks — the how

Plain prose, no tool names, no product names. Refers only to abstract operations the config is required to supply: create a ticket, move a ticket, compile, test, commit, open a pull request. Also holds the state machine, the change taxonomy, the failure doctrine, and the definitions of the review agents.

One copy per machine · every project points at it

L2

Project config — the where

One config file per repository. Declares the tracker and its field mapping, the ordered verification chain, the commit convention, the branch and push policy, and the repository's hard rules. Written once by the installer from a stack preset, then edited by hand.

Per repository · read by every playbook

L3

Agent adapter — the wiring

Generated pointers that make the core discoverable to one specific agent, in whatever file format that agent reads. Each adapter also declares what its agent lacks, because a playbook needs to know which of its assumptions don't hold. Never committed — they are derivable from the config, and one person's choice of agent shouldn't land in everyone else's tree.

Per agent · generated · never committed

04 — Operator profile

The agent needs to know who it is working for

Not personality decoration. This layer exists because a handful of facts about the operator change what an agent should actually do — which stack it is in, which language to answer in, which actions require permission first, and what counts as evidence.

Required fields

FieldWhat it declaresWhat changes without it
role Seniority and discipline, and the depth of explanation expected alongside a change. The agent hands over a diff with no reasoning, or explains fundamentals to someone who wrote them.
contexts The named environments the operator moves between, each with its stack and its stakes. One entry per repository family. Conventions from one stack leak into another, and risk is judged uniformly across environments with very different consequences.
language Default reply language, plus any per-context override, plus the rule that the operator's own messages decide — never the surrounding context. The agent takes its language from memory files or system text and answers in the wrong one.
permission Which classes of action require asking in the current conversation rather than relying on precedent: anything outward-facing, destructive, or irreversible. Approval granted once gets treated as standing, which is how production gets touched.
evidence What the operator accepts as proof. Typically: verify against the source before asserting, and treat stored notes as dated claims rather than current fact. The agent agrees confidently, cites a stale memory, and both parties act on something no longer true.
authorship Commit conventions and whether generated work may be attributed in the history. Trailers and co-author lines appear in a history that was supposed to stay clean.
interaction How the operator wants to be engaged: whether to push back, whether to offer alternatives with trade-offs, and that a question ends the turn rather than being answered by the asker. The agent asks and then answers itself, or agrees with a wrong premise to stay agreeable.
tooling Preferred commands and anything explicitly banned from the shell. Muscle-memory defaults get used where the operator has deliberately chosen otherwise.

Why this is a layer and not config

Because it does not vary by repository. Declaring the same identity in three config files means three places to update and three chances to drift. The profile is the one part of the harness that follows the person.

05 — State machine

Seven states, mapped onto whatever the tracker already calls them

The harness thinks in seven states. Config maps each to a real value in the real tracker, so adopting this never requires renaming a column or restructuring a board.

captured→ queued→ running→ verified→ in‑review→ shipped · blocked
StateMeaningWho may write it
capturedWritten down, not triaged. Outside the queue.human
queuedIn the queue, ready to run, ordered by severity then age.both
runningBeing worked. Exactly one at a time per branch.both
verifiedCompiles, tests pass, reviewed, committed — not pushed.harness
in-reviewIncluded in the run's open pull request.harness
blockedThis task is stuck and set aside. Its work is stashed, the queue continues.harness
shippedMerged and released to users.human only

The harness never says "done"

Its terminal state is in-review, with a pull request open and every included ticket linked to it. Whether something is genuinely finished is a judgment about users, and that stays with the person who merges and deploys.

Iteration is whatever the project already uses

There is no sprint object in the harness. The config points one key at whatever the project treats as its current iteration — a cycle, a sprint, a milestone, a version in development. The playbook only ever asks for the current iteration and lets the tracker layer resolve it. A team running two-week cycles and a solo project shipping versions both satisfy the same contract.

06 — Change taxonomy

One field on the ticket decides the commit type

Every ticket declares the nature of its change. This is not metadata for filtering — the commit message derives from it, which is what stops a ticket being a wish and makes it an instruction.

ChangeCommitWhen
addfeatSomething that did not exist before
changefeatIt existed and now behaves differently
removefeatSomething is taken out
fixfixIt goes back to doing what it already promised
refactorrefactorSame behaviour, better code
toolingchoreBuild, deploy, scripts, documentation

This is the portable core. Config may extend it, and a domain usually needs one or two entries of its own — a category that would otherwise get mislabelled every time, mapped to whatever commit type that domain already uses.

Two constraints on any extension. It must be small enough that the right answer is obvious: a twelve-option picker guarantees a wrong pick, and a wrong pick here silently corrupts commit history. And every entry must map to exactly one commit type, or the field stops being able to decide anything.

The same field also drives the ticket's icon, which makes a board legible at a glance without reading a single title.

07 — Config schema

Every project-specific noun, in one validated file

This is where agnosticism is either real or merely claimed. If a key is missing here, a playbook somewhere is guessing — and the fix is a new key, never a sentence added to the core.

KeyPurposeShape
harness.version The core version this repository was written against. Checked at the start of every run: a minor mismatch warns, a major one refuses. The safety belt for a single global core shared by several projects. Semantic version
stack Selects the preset the installer starts from and the conventions the playbooks assume about file layout. One preset name
tracker.kind Which tracker backend document to load. Determines how every ticket operation is performed. One backend name
tracker.board The board, project, or team the queue is read from. An environment variable reference, never a literal identifier in a committed file. Env reference
tracker.states Maps each of the six harness states to the literal value this tracker uses. The whole state machine is portable because of this map. State → string
tracker.iteration Where "the current iteration" comes from, and the condition that identifies which one is current. Source + predicate
tracker.assignee Who new tickets are assigned to, when the tracker models people at all. Identity or omitted
tracker.shared Whether humans also write the mapped states. When true, the harness marks its own entries and ignores unmarked ones in silence. Boolean
tracker.marker_field The text field the ownership marker is written into. Required whenever the board is shared. Field name
tracker.cache_ttl How long a queue read may be reused. Exists because rate-limited query APIs are common and a status check should not spend quota. Duration
verify[] The ordered gate. Each entry names a check, how to run it, and the condition that counts as passing. Runs in sequence; the first failure stops the task. Ordered list
verify[].scope How narrowly a check may be run — the narrowest relevant suite first, widening only for broad changes. Scope hint
vcs.branch Branch policy: stay on the current branch, or derive one per ticket from a pattern. Policy or pattern
vcs.push Whether the harness may push, must ask first, or never pushes. Pushing is outward-facing, so the default is the most conservative option and anything else is a recorded authorisation. never · ask · always
vcs.pr.enabled Whether the ship playbook runs at all. A repository with no review culture stops at verified and committed. Boolean
vcs.pr.granularity One PR per run, or one per ticket. Per-ticket requires a branch-per-ticket policy; the two keys are validated together because the wrong pairing silently produces one PR that swallows the run. run · ticket
vcs.pr.draft Whether the PR opens as a draft and when it is marked ready — typically at the end of a clean run. Policy
vcs.pr.link How a PR references its tickets. A URL in the body for trackers that live elsewhere; a closing keyword and issue number for trackers native to the forge. url · issue-ref
vcs.attribution Whether generated work may be credited in commit trailers or PR bodies. Applies to both or neither — a clean history undermined by a PR footer is not a clean history. none · pr-only
vcs.language The language commit messages are written in, independent of the reply language. Language code
vcs.commit_map Change taxonomy entry to commit type. Extends the portable core for this domain. Change → type
rules[] Hard prohibitions specific to this repository, injected verbatim into every sub-agent prompt. The escape hatch that keeps local exceptions out of the core. List of statements
preflight[] Conditions checked once before a run starts, each able to halt it: toolchain reachable, no conflicting editor state, expected branch, clean working tree, and — whenever pushing is enabled — that the current branch is not the default one. List of checks

What the installer fills in, and what it refuses to guess

Stack detection reads what is on disk and picks a preset, which supplies sensible defaults for most keys. The verification chain is the exception: the installer proposes it and requires confirmation, because this is the one place the harness can be actively dangerous rather than merely useless. A gate that always passes is worse than no gate — it converts unverified work into work stamped as verified.

08 — Invariants

Five rules the whole thing rests on

InvariantWhy it exists
The tracker is truth.
Local state is a cursor.		 The local file caches queue order and which ticket is running. Delete it and it rebuilds from the board — the running ticket is the one in the running state. No state exists only on one disk, so a second machine or a fresh session is never blind.
The gate is delegated,
never invented.		 Verification is whatever the project declares, run by the review-and-fix playbook. The harness reads a pass or a fail; it never decides for itself that code is fine. Where an executable check exists, an opinion does not count.
A stuck task steps aside.
A broken environment stops everything.		 Two different failures deserve two different answers. A task that can't be finished has its work moved to a named, recorded stash, its ticket marked blocked, and the queue carries on — one bad ticket shouldn't freeze the other nine. A broken environment stops the run outright, because without a working gate nothing after it can be verified. Never discard work: stash it, record the reference and the message, and report where it is.
Planning is the exception. Spec-driven planning triggers only for protocol changes, migrations, anything touching money or persistence, work spanning several subsystems, or an unresolved product decision. Everything else goes direct. A three-line fix that gets a design document teaches everyone to skip design documents.
One writer for history
and for the tracker.		 The orchestrator commits and updates the board; sub-agents implement and report. Two writers on one piece of state is how history becomes unattributable and a board starts to lie.
09 — Field notes

Two defects that only appeared when it ran

Both survived design review and died within minutes of contact with real data. They are recorded here because each one generalises well past this harness, and because a spec listing only what works is a brochure.

Defect 01 — surfaced by a read-only status call

The board is shared, and the design assumed it was not

The state machine treated running and blocked as belonging to the harness. In reality the board already held several tickets parked in the running state as personal work-in-progress, and more in the blocked state used as frozen backlog. On its first run the harness would have halted demanding answers about tickets that were never its own, and its genuine failures would have been indistinguishable from a human's parking spot.

Fix: states are shared; a marker written into a text field disambiguates ownership. An entry without the marker belongs to the human and is ignored in silence — not queued, not reported, not asked about. A marker in an existing text field was chosen over a new column so adoption requires no schema change and the board stays readable to someone who has never heard of the harness.

Generalises to: before designing on top of a shared external system, look at how it is actually used, not at what its schema permits. A status field with seven options does not imply each option has one owner.

Defect 02 — surfaced only at implementation time

"Can't do X" has two opposite readings

A ticket phrased as an inability was triaged as a complaint: a limit exists, remove it. Investigation confirmed no limit existed anywhere in the code, and that finding was read as the limit is emergent — producing a plan to raise capacity. The actual request was the reverse: please add a limit. "No limit exists" was not a clue. It was the answer.

Fix: create-task resolves that ambiguity by asking, before any investigation begins. No amount of code reading disambiguates it, because both readings are consistent with the same code.

Generalises to: the same trap hides in "X is missing" — broken, or never built? — and in "X doesn't work as expected", where the expectation is the undeclared half. One question costs a turn. An inverted ticket costs a full implementation; this one cost exactly that, and the queue caught it only because failure stops instead of continuing.

10 — Install

Cloned once. Wired per repository. One committed file.

The harness lives in exactly one place on a machine. A project doesn't receive a copy — it receives a pointer and a config file, and the config file is the only thing that enters version control.

Home — one clone per machine

~/.harness/
├─ profile/                  # L0 — the operator, one per human
├─ core/
│  ├─ create-task
│  ├─ start-task
│  ├─ pipeline
│  ├─ review-and-fix
│  ├─ ship
│  └─ state-machine          # no tool names live anywhere in here
├─ agents/                   # reviewer · critical-reviewer · fixer
├─ schema/                   # L2 — validates every config file
├─ presets/                  # one per stack
├─ trackers/                 # one per backend: how to speak it
├─ adapters/                 # L3 — templates, one per agent
└─ bin/                      # the installer

A project after init — what is tracked, and what is not

your-repo/
├─ .harness/
│  ├─ config.yml             COMMITTED — the only file that is
│  └─ state.json             excluded — machine-local cursor
├─ <agent adapter files>     excluded — generated pointers
└─ .git/info/exclude         local-only ignore, never travels

Why only the config is committed

Config is project truth — the verification chain, the state mapping, the repository's hard rules. It belongs in review like any other project configuration, and it is safe to commit because it holds environment-variable references, never literal identifiers or tokens.

Adapters are generated pointers to the global core. Committing them would be committing build output, and it would push one person's choice of agent into everyone else's tree. A teammate who adopts the harness runs init against the committed config and gets adapters shaped for their agent — a better outcome than inheriting yours.

The exclusion uses the repository's local-only ignore file rather than the shared one. Personal tooling should not appear in a shared ignore list, and using the local mechanism means the harness can be installed into a repository whose ignore rules you have no business editing.

Cloning that repository on another machine therefore yields the config and nothing else — which is sufficient. Re-running init reads the existing config and rebuilds every adapter. Config being committed is precisely what allows adapters not to be.

One global core needs version pinning to be safe

The cost of a single shared copy is that updating it changes behaviour everywhere at once, including in a project mid-run. So the committed config declares the harness version it expects, and every playbook checks it before starting. While the core is 0.x, a minor mismatch refuses to run — 0.x minors are breaking by semver convention, and the 0.1 → 0.2 playbook rename is exactly the kind of change this check exists to catch; a patch mismatch warns. From 1.0.0 the usual rule applies: major refuses, minor warns. Recovery is always the same: re-run init to regenerate the adapters, then bump the pinned version.

Without that check, "one global copy" is a footgun — an upgrade for one project silently rewrites the rules of the other two. With it, drift is loud, and each repository states in version control which contract it was written against.

What init does

  1. 01Ensure the core existsClone it to the home location if this machine doesn't have it yet, otherwise use what's there. Updating the harness is a pull in one directory.
  2. 02Detect the stackReads manifests, project files and lockfiles, then selects a preset. Ambiguous or unrecognised repositories get asked rather than assumed.
  3. 03Choose the trackerPick a backend and point it at a board through an environment variable. One connection reaches one workspace, which is why this is per-project config and not a global setting.
  4. 04Map the statesRead the tracker's existing status values and map the harness states onto them. Nothing in the tracker is renamed or restructured.
  5. 05Confirm the verification chainThe preset proposes an ordered gate; the operator confirms or corrects it before anything is written. This is the only step that cannot be skipped.
  6. 06Generate adaptersWrite pointer files for the agents actually in use. Each records what its agent lacks, so the playbooks adapt instead of assuming. Never edit a tracked file the harness doesn't own — if an agent's manifest already exists in version control, stop and ask rather than appending to it.
  7. 07Commit one, exclude the restEmit the config for version control; add the adapters and the cursor file to the local-only ignore. Print exactly what was written and what was excluded, so nothing about the install is implicit.

Connecting the integrations

The harness assumes nothing about credentials. Each tracker document lists the server it needs and the minimum capability it depends on — typically the ability to query a collection of tickets and update one. Because a single connection reaches a single workspace, a personal tracker and a work tracker coexist without either knowing the other exists.

This document is the specification, not a description of something already finished. The four playbooks and one tracker backend exist and have run against real work; the config layer, the installer, the second adapter, and the profile are what this page defines.
